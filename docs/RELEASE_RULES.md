# 发版（Release）内容规则

> **硬性要求：每一个 Release 都必须写清楚「这个版本新增了什么 / 修复了什么」。**
> 只放一个标题、只贴资产哈希表、或者只写「详见 README」都算不合格。
> 用户点开 Release 页面的第一眼，就应该知道这一版值不值得升级。

- 适用范围：V 系列 `V主.次.修`、X 系列 `X<MMdd>[Y<序号>]`
- 唯一事实来源：仓库里的 `NOBS/RELEASE_NOTES_<tag>.md`（V 系列 / X 系列）
- 自动化：CI 的 release job 会读取这份文件作为 Release 正文，并在末尾追加资产 SHA-256 表。
  **文件不存在或内容过短时，发版 job 直接失败**，不允许「空说明发版」。

---

## 1. Release 正文必须包含的 6 个部分

| 顺序 | 部分 | 要求 |
| --- | --- | --- |
| 1 | **一句话摘要** | 这一版最值得升级的一件事，1–3 行；不要写「若干优化」这种空话 |
| 2 | **新增功能** | 逐条列出用户能感知到的新能力；每条写「怎么用 + 有什么用」 |
| 3 | **修复的问题** | 逐条列出修了什么、以前是什么表现、现在是什么表现 |
| 4 | **兼容性与升级** | 能否增量升级、设置 / 数据是否保留、热键 / 协议 / 系统要求有没有变化 |
| 5 | **已知边界** | 这一版仍然不保证的事情（没有就写「无」） |
| 6 | **下载与校验** | 安装包 / 便携包 / 增量包文件名；校验和由 CI 自动追加，不需要手写 |

> 如果没有新增功能（纯修复版），第 2 节写「本版无新增功能，只修复问题」；
> 如果没有修复（纯功能版），第 3 节写「本版无修复项」。**这两节不能整节省略。**

## 2. 写作要求

- **面向用户**：说清楚「你会看到什么变化」，不要只写内部类名、文件名、重构细节；
- **可核对**：修复项尽量写「以前 → 现在」的对比；性能 / 体积类变化给出数字；
- **不夸大**：未验证的能力不要写成已支持；捕获排除、Win7 兼容等边界照实写；
- **文件名与版本一致**：正文里出现的安装包 / 便携包 / 增量包文件名必须是本版真实产物；
- **不重复仓库文档**：可以链接完整文档，但 Release 正文本身必须能独立读懂；
- **中文为主**：英文版 README 可以同步，但 Release 正文至少要有完整中文说明。

## 3. 文件命名与位置

| 版本类型 | 文件 | 分支 |
| --- | --- | --- |
| V 正式版 `V3.5.3` | `NOBS/RELEASE_NOTES_v3.5.3.md` | `master` |
| X 系列 `X1031` | `NOBS/RELEASE_NOTES_x1031.md` | `master` |
| X 同日再版 `X1031Y2` | 仍为 `NOBS/RELEASE_NOTES_x1031.md`（按日期归档） | `master` |

- 文件名与 tag 的对应关系（CI 会**去掉 tag 开头的 `V` / `X`** 再找文件）：
  - tag `V3.5.3` → **`NOBS/RELEASE_NOTES_v3.5.3.md`**，最后兼容 `NOBS/RELEASE_NOTES_3.1.1.md`；
  - tag `X1031` / `X1031Y2` → **`NOBS/RELEASE_NOTES_x1031.md`**（X 系列按日期归档，`Y` 序号不单独建文件）；
- 为避免歧义，V 系列统一用 **`RELEASE_NOTES_v<版本>.md`**（小写 v）；
- 仓库只维护 `master` 一个分支，发布说明只放 `master`（见 [`BRANCH_AND_DOC_RULES.md`](BRANCH_AND_DOC_RULES.md)）。

## 4. 发版流程（与内容有关的部分）

1. 写 / 更新 `NOBS/RELEASE_NOTES_<tag>.md`，按上面 6 个部分自检；
   X 系列写到按日期命名的文件（如 `X1031Y2` → `RELEASE_NOTES_x1031.md`）；
2. 确认正文里的版本号、文件名、系统要求与 `csproj` / 安装包一致；
   X 构建的内部版本由 `build.ps1 -Version` 覆盖（`X1031Y2` → `1031.2.0`），csproj 保持 V 版本；
3. 提交到 `master`；
4. 打 tag 并推送：CI 会用这份文件作为 Release 正文，并追加资产 SHA-256 表；
5. 发版后打开 Release 页面**逐条核对**：摘要、新增、修复、升级说明是否都在；
6. 如果发现正文被覆盖或缺失，先修 `RELEASE_NOTES_<tag>.md`，再重跑 release job
   （或 `gh release edit <tag> --notes-file NOBS/RELEASE_NOTES_<tag>.md`）。

## 5. 禁止事项

- ❌ Release 正文只有标题 + 资产哈希表（CI 早期就是这样，V3.1.1 已修正）；
- ❌ 只写「详见 README / 详见发布说明」而不写更新内容；
- ❌ 把内部重构清单当作用户更新说明；
- ❌ 正文里的文件名 / 版本号与实际产物不一致；
- ❌ X 系列同日再版另建 `RELEASE_NOTES_x1031Y2.md`（应按日期共用 `RELEASE_NOTES_x1031.md`）。

## 6. 提交前检查清单

- [ ] 有 `NOBS/RELEASE_NOTES_<tag>.md`，且放在正确分支；
- [ ] 一句话摘要能说清「为什么升级」；
- [ ] 新增功能逐条列出（没有就明确写「无新增功能」）；
- [ ] 修复项逐条列出，并写清「以前 → 现在」（没有就明确写「无修复项」）；
- [ ] 写清能否增量升级、设置 / 数据是否保留；
- [ ] 已知边界照实写；
- [ ] 文件名、版本号、系统要求与产物一致；
- [ ] 发版后到 Release 页面实际核对过正文。

## 7. 已发生的纠正（V3.1.1）

- CI 的 release job 原先把 Release 正文**整体覆盖**成「标题 + 资产 SHA-256 表」，
  导致 V3.1.1 发布说明没有出现在 Release 页面；
- 现在 job 改为读取 `NOBS/RELEASE_NOTES_<tag>.md` 作为正文，再追加 SHA 表；文件缺失 / 过短时直接失败；
- V3.1.1 的 Release 正文已按本规则补回「新增 / 修复 / 升级 / 下载」内容。
