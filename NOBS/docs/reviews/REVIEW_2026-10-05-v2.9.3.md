# V2.9.3 代码审校记录（三轮）

> **关于「独立」二字**：这三轮由同一执行方按**不同视角**分轮进行，不是三个互相不知道对方结论的人。
> 因此这里对每条结论都标注了**证据类型**：
> `[机器]` = 有单测 / 构建 / 解码器等可复现证据；`[人工]` = 只能靠对读与推理，
> 结论强度弱于前者。真正意义上的独立复核（换人换实现）不在本次范围内，不作宣称。

审校范围：V2.9.3 的全部改动（内容英译 + 按语言装载 + 热更新分发 + 一键部署录制环境 +
下载/反馈入口 + 双目标 Windows 7 兼容 + 构建链路 + 测试与文案）。

---

## 第一轮：数据安全与出站行为

关注「这个版本会不会**改坏用户的东西**或**把用户带到不该去的地方**」。

### 1.1 写用户配置前必须先有退路 —— 通过 `[机器]`+`[人工]`

- `RecordingEnvService.ApplyAsync` 在任何写入之前先 `CreateBackupAsync`，
  **备份失败即中止**并返回明确文案（`env.backupFailed`），不会「没有退路也照改」；
- 文件通道额外落一份同目录 `.obshelper.bak`；
- 写入后**重新读回逐项校验**（`env.readBackMismatch` 会指名哪个参数期望值与实际值不符），
  而不是写完就当成功 —— 「写没写进去不能靠我以为写对了」；
- 每个参数在写入前把旧值记进 `Rollback`，回滚就是把旧值写回去（同样的读口径）。

`[机器]` 证据：`RecordingEnvCoreTests` 覆盖 INI 打补丁的保真性 ——
同节同名才替换、注释行不动、同名的跨节键不受影响、CRLF 行尾保留、
补丁后一定能读回目标值（4 组前提 × 逐一断言）。

### 1.2 不碰用户自己选的推流配置 —— 通过 `[机器]`

`RecordingEnvCoreTests.Build_TargetsOnlyRecordingRelatedParameters` 断言推荐项**只**涉及
录制相关参数，显式排除 `Mode` / `StreamEncoder` / `VBitrate`。
改输出模式会连带影响推流，属于用户自己的选择，本版不碰。

### 1.3 出站白名单：官方源与备用通道必须分开 —— 通过 `[机器]`

- `ObsDownloadLinks.IsOfficialDownloadUrl` 仍只认 https + `obsproject.com`（含官方 CDN 子域）
  + `github.com/obsproject/obs-studio`；新增的 `IsTrustedAlternativeChannel` 只认
  `steampp.net` / `apps.microsoft.com`，**两者不共用白名单** ——
  否则「只从官方渠道下载」这句防伪提示就失真了；
- 应用内下载在解析出直链后**再校验一次**官方域名，不通过就直接拒绝（`obs.dl.insecure`）；
- 反馈入口 `FeedbackLinks.IsTrustedFeedbackUrl` 限定 `docs.qq.com` 与本仓库 Issues，
  同前缀仿冒域（`docs.qq.com.evil.example`）与 http 一律拒绝。

`[机器]` 证据：`DownloadChannelTests` / `FeedbackLinksTests` 覆盖上述正反例。

### 1.4 二维码内容与按钮地址不得漂移 —— 通过 `[机器]`

二维码是「隐形入口」：一旦与按钮指向的地址漂移，扫码用户会被送到另一个页面**而没有任何提示**。
`FeedbackLinksTests.QrPayload_EqualsFormUrl` 把两者钉成同一个常量；
`[机器]` 另有端到端证据：生成脚本用两个互不相关的编码实现交叉核对，
**再用独立解码器（zxing-cpp）把生成的 PNG 读回来**，断言解出文本与表单地址逐字符一致
（实测输出 `https://docs.qq.com/form/page/DSXJMWkNDYVFUWHBo`）。

### 1.5 出站 URL 不落第三方 —— 通过 `[人工]`

逐条核对本版新增的所有外链字面量：`steampp.net`、`apps.microsoft.com/detail/XPFFH613W8V6LV`
（微软商店官方商品页，OBS 官网下载页的「Get it from Microsoft」指向同一 ID）、
`docs.qq.com/form/page/…`、GitHub Issues。均无短链、无跳转服务、无 http。

### 1.6 首轮发现并修掉的问题

| 问题 | 处置 |
|---|---|
| 下载失败时叠了一个占位符为空的 toast（`obs.toast.linkFailed` + `""`），显示成「打不开链接：」 | 去掉；失败原因已在状态行里给足（含两条退路） |
| 二维码资源缺失时留下一个白色空框 | 整格收起，并把原因并入说明文字 |
| `RecordingEnvCard` 在渲染逐项结果**之后**又刷新了列表，把刚画的结果清掉 | 调换顺序：先刷新再渲染结果 |

## 第二轮：双目标与构建边界

关注「兼容构建会不会悄悄降低能力」「两个 TFM 会不会产出错东西」。

### 2.1 兼容层只做语义等价的替换 —— 通过 `[机器]`+`[人工]`

| 差异 | 处置 | 等价性 |
|---|---|---|
| `required` 成员属性（.NET 7+） | 编译期 polyfill（`Compat/RequiredMembers.cs`，`#if !NET7_0_OR_GREATER`） | 仅补类型声明，无运行时行为 |
| `char.IsAsciiDigit` / `IsAsciiLetterOrDigit`（.NET 7+） | `Compat.IsAsciiDigit` 等 | 与原实现逐字符等价（ASCII 数字 / 字母） |
| `AesGcm(key, tagSize)`（.NET 8 起） | `Compat.CreateAesGcm` 统一 16 字节标签 | 两条分支**密文完全一致**，见下方风险说明 |
| `OpenFolderDialog`（.NET 8 起） | `FolderPicker`：net8+ 用 WPF 版，net6 退到 WinForms 版 | 都返回「绝对路径 / 取消时 null」，调用方无感知 |

`[机器]` 证据：`dotnet build -c Release` 对 `net10.0-windows;net6.0-windows` 双目标
**0 warning 0 error**（NETSDK1138「net6.0 已 EOL」提示除外，属预期）。

### 2.2 ⚠️ 风险与证据边界（**必须如实记录**）

- **`Compat.CreateAesGcm` 的加密兼容性没有专门的往返测试**：结论「两条分支密文一致」来自
  「标签长度都是 16 字节、密钥 / nonce / 明文相同 ⇒ 输出相同」这一推理，
  **不是实测**。现有 `ObsAuthTests` 覆盖的是认证字符串，不是 `secrets.dat` 的加解密。
  V2.9.3 之前写入的密文能否被新构建读取，取决于「同一 TFM 内构造参数没变」——
  主构建从 `AesGcm(key, 16)` 换成 `CreateAesGcm(key)` 后仍展开为 `AesGcm(key, 16)`，
  因此**主构建侧零变化**；兼容构建是新引入的产物，没有历史密文。
  结论：实际风险低，但**不做「已验证」的宣称**。
- **Windows 7 真机未验证**：本轮只做到「目标框架可编译 + 安装包 MinVersion 正确下发」。
  没有 Win7 SP1 机器跑过启动、托盘、WPF 渲染与 DPAPI 路径。
  README 与发布说明按此如实描述为「兼容构建」，不写「已在 Win7 上实测通过」。

### 2.3 安装包与资产命名 —— 通过 `[机器]`

- `.iss` 的 `MinVersion` 由 `build.ps1` 按 TFM 传入：主构建 `10.0`、兼容构建 `6.1sp1`。
  这是「装得上但跑不起来」的最后一道拦截（用户看到的是「双击没反应」而不是可照做的提示）；
- 两个 TFM 共用同一个 AppId（同一款软件，Inno 才会把换构建识别成升级而非并存装两份），
  该取舍已写进 `.iss` 注释；
- `build.ps1` 导出**四份**知识库/插件资产（中英 × 两类），命名带版本号。
  `[机器]` 证据：`KnowledgeBaseUrlsTests.RawUrls_MatchFilesInSourceTree` 对**四份**资产
  逐一校验仓库相对路径在本机源码树里真实存在。

### 2.4 第二轮发现并修掉的问题

| 问题 | 处置 |
|---|---|
| `ContentAssets` 直接引用 `FileLogger`：一来会**破坏单测工程的链接编译**（FileLogger 不在那个编译单元里），二来让「纯逻辑」文件耦合了日志实现 | 改为通过 `out bool fellBackToChinese` 把回退事实交给调用方，各 Service 自己写 WARN |
| Release 资产匹配器不区分语言：中英资产挂在同一 Release 上，会被同一个匹配器同时认下，中英用户互相拿到对方的文件（**静默**：内容合法、解析成功，只是语言不对） | 新增 `UpdateService.AssetMatchesLanguage`；`ReleaseAssetLanguageTests` 断言中英匹配结果互不相交 |
| `Version` 比较经典坑：`6.1.7601 < 6.1.7601.0` 成立（未指定段按 -1 参与比较），会导致「手里的 6.1.7601 不是 Win7 SP1」这种荒谬结论 | `OsSupport.Normalize` 统一补成四段再比；`OsSupportTests` 按档逐一钉住 |
| `build.ps1` 被我改写的工程路径解析写错（找不到 `.csproj` 直接构建失败） | 修正为「脚本在 NOBS/ 下、工程在 NOBS\OBS_Helper.Wpf\」 |

## 第三轮：交互、文案与一致性

关注「用户看到的每一处是不是都是对的」。

### 3.1 语言切换的完整闭环 —— 通过 `[机器]`+`[人工]`

链路：`LocalizationService.Changed` → `AppServices.OnLanguageChanged` → 丢弃
知识库/插件目录/场景模板缓存（只对**已创建**的服务调 `Reload`，避免把 OBS 连接服务提前拉起）
→ 补刷当前语言的热更新内容。

`[人工]` 核对：各 Service 内部的 `InvalidateOnLanguageChange()` 与语言事件是**双保险**，
即使事件链断了，读数据时也会按语言重建缓存。
`[机器]` 证据：`ContentAssetsTests` 覆盖命名与回退次序；`EnglishContentTests` 覆盖资产形状。
⚠️ `[人工]` **证据边界**：没有自动化 UI 测试真的切一次语言并逐页截图，
「切完每页都对」这条结论来自代码路径推理 + 既有 V2.9.2 的语言往返自检。

### 3.2 文案键与界面引用一致性 —— 通过 `[机器]`

- 中英两表键集完全一致、无重复、无空值（既有 `StringsTests`）；
- 英文表里不出现汉字；
- XAML 引用的每一个 `Loc.*` 都真实存在：本版新增的
  `Loc.env.*` / `Loc.obs.dl.*` / `Loc.obs.toolkit` / `Loc.obs.msStore` /
  `Loc.feedback.*` / `Loc.common.cancel` 全部落下，`StringsTests` 的
  `XamlLocKeys_Resolve`（读取全部 XAML 里的 `{DynamicResource Loc.*}`）覆盖；
- `[机器]` 人工脚本复核：两表各 **1741 键**，差集为空。

### 3.3 「看得见才好排查」这条项目原则 —— 通过 `[人工]`

逐条检查本版新增的失败路径是否有可读出口，而不是静默：

| 场景 | 用户看到 |
|---|---|
| 英文资产缺失 | 该处退回中文内容 + 日志 WARN（不是静默中文） |
| 一键部署：找不到配置目录 / OBS 在跑但没连上 / 读不到 basic.ini | 三档各自的阻断原因文案，按钮置灰 |
| 一键部署：写入校验不一致 | 指名是哪个参数、期望值与实际值 |
| 应用内下载：拿不到直链 | 说明「已改为打开发布页」并真的打开，而不是假装在下载 |
| 应用内下载：直链不在官方域名下 | 明确拒绝下载 |
| 二维码资源缺失 | 收起二维码格 + 「请用上面的按钮」 |
| 结果条目拿不到文案键 | 显示原始参数名，而不是把 `env.item.BaseCX.label` 糊到界面上 |

`[人工]` 发现并修掉：`RecordingEnvCard` 的结果区被随后的刷新清空、结果显示半成品键名
（**注意**：这两条最初是我自己在写实现时埋下的，属于同轮内的自我发现，
证据强度低于「第二个视角发现的问题」）。

### 3.4 英译文本的用词与术语 —— 部分 `[机器]`、部分 `[人工]`、**存在已知边界**

- `[机器]`：中英逐条对等（条数 / id 序列 / 各数组长度 / `links[].url` / 分类 id 一一对应）；
  英文侧无汉字与全角标点；`severity` / `level` / `badge` 取值落在 `DataValues` 认识的串内；
  场景来源名一致且不撞名；指引的标题层级、代码围栏数、链接 URL 与中文版逐一对应；
- `[人工]`：术语表（Scene / Source / Encoder / keyframe interval / Display Capture…）
  按英文版 OBS 界面用词统一；症状词（黑屏 / 掉帧 / 爆音）在英文标题里以对应英文词保留，
  以保证搜索命中率；
- ⚠️ **已知边界**：**没有对着英文版 OBS 逐条核对菜单路径的逐字一致性**。
  译文里的 `Settings → Output → Recording` 这类路径是按英文版 OBS 通行写法翻译的，
  不是逐条实测（本轮无英文版 OBS 环境）。这一条**不作「已对齐」的宣称**。
  同理，英译未经过母语者校订，属「技术准确、风格一致」，不等于「出版级地道」。

## 明确未验证的事项（不做过度宣称）

1. **Windows 7 SP1 真机运行**：只有「可编译 + MinVersion 正确」，无真机验证；
2. **`Compat.CreateAesGcm` 跨 TFM 密文一致性**：推理成立，但无往返测试；
3. **英文版 OBS 菜单路径逐字对齐**：无英文版 OBS 环境核对；
4. **英译的母语者校订**：未进行；
5. **一键部署在真实 OBS 实例上的落地效果**：`obs-websocket` 与 `basic.ini` 两条通道
   均按协议 / 键名实现并有单测，但**没有对真实 OBS 跑过一次端到端落地**；
6. **切语言后逐页人工走查**：只有代码路径推理与既有自检覆盖。

以上 6 条都不影响「编译通过 / 单测全绿 / 安装包能装」这类结论，
但都会改变「已经验证到什么程度」的判断，因此单列出来。
