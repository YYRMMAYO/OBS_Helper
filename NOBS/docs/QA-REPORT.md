# OBS帮助助手 · 质量与审查报告索引（QA-REPORT）

> 本文件是**索引**，不是审查报告本身：本仓的历史审查 / 优化评估记录分散在
> `docs/`（优化清单与设计稿）与 `docs/reviews/`（发布审查记录）两处，条目多、命名带日期，
> 直接翻目录很难判断「哪一份对当前版本还有效」。这里把入口集中成一张表。
>
> **本文件原先是一个 0 字节的空文件**（V2.9.6 复核时发现）。空文件比没有更糟：
> 目录里看着有一个「QA 报告」，点进去什么都没有，读者只会以为质量记录缺失。
> 因此补成索引而不是删除 —— 记录本身是有的，只是缺一个入口。

## 1. 怎么用这张表

- **「结论是否仍然有效」列是这张表最重要的信息**。审查记录带日期，它们描述的是**当时那一版**的事实：
  里面的版本号、知识库条数、测试项数、自检项数**都会过期**。
  引用某一版的数字之前，先看这一列；需要当前数字请以 `README.md` 与
  [`scripts/check_docs.py`](../scripts/check_docs.py) 的实测结果为准。
- 每一份报告都保留**当时的原文**。本仓刻意不「回填」历史报告的结论 ——
  把过期数字改新会让「当时的判断依据」永久丢失。要纠正，就在报告里追加一段带日期的备注，
  或像 `docs/FEATURES_USERVIEW_2026-10-05.md` 那样在文首加一行过期提示。

## 4. 复查与新增记录时的约定

1. **每条结论标证据类型**：`[机器]`（有单测 / 构建 / 脚本等可复现证据）与 `[人工]`（只能靠对读与推理）
   分开标，不要把推理写成实测。V2.9.3 / V2.9.4 两份记录已经这么做了，沿用即可。
2. **不要宣称「独立复核」**，除非真的换了人或换了实现 —— 同一执行方按不同视角分轮不算独立。
3. **数字一律给基线版本**（「V2.9.6 实测 N 条」），不要写「约 N 条」这种无锚点的说法；
   可以自动核对的数字交给 [`scripts/check_docs.py`](../scripts/check_docs.py) 钉住。
4. **新报告命名**：发布审查放 `docs/reviews/REVIEW_<日期>-v<版本>.md`；
   面向后续版本的优化清单与缺口指引放 `docs/`，文件名带月份。
5. 新增报告后回填本文件的表格。
