## 2. 根因

V3.5.1 的「停止录制后仍显示录制中」不是单一 UI 问题，而是三层叠加：

1. **事件之后的查询会短暂报错状态**：OBS 发出 `RecordStateChanged(STOPPING/STOPPED, outputActive=false)` 之后，`GetRecordStatus` 仍可能返回 `outputActive=true`（实测约 0.5–1 秒）。旧实现把这次「补齐查询」的结果直接写回 `Active`，把刚停止的录制翻回运行中；此后没有新事件来纠正。
2. **批量查询协议发错**：旧代码把批量当成 `requestType = "CallBatch"` 的普通请求（OBS 回 204），执行方式又传字符串 `"Parallel"`（OBS 以 4004 断开）。连接后的输出状态 / 音频静音 / 音量刷新全部静默失败，状态只剩事件一条通道。
3. **批量 Parallel 结果会串位**：改用正确的 op 8 / op 9 后，OBS 33.0.1 / obs-websocket 5.7.6 在 `executionType=2 (Parallel)` 下会把 `results[].responseData` 错配到别的子请求（录制 / 推流 / 虚拟摄像头互相串位）；`0 (SerialRealtime)` 与 `1 (SerialFrame)` 正确。

修复：

- 状态事件是权威来源；事件触发的补齐查询只写 `timecode` / `bytes` / `paused`，不写 `Active`。
- 连接期间每 3 秒做一次轻量对账；查询与事件冲突时 3 秒内以事件为准，事件过期才采信查询。
- 批量请求改为 `RequestBatch`（op 8）/ `RequestBatchResponse`（op 9），执行方式用数字枚举并默认串行。
- 手机页面刷新 / WS 重连前先向 OBS 对账；状态灯按 `streaming` / `recording` 区分文案；非运行状态计时器归零。

## 6. 已知边界

- **未做 Authenticode 代码签名**：需要开发者本人的代码签名证书与私钥，仓库内没有该证书；SmartScreen 仍可能提示「未知发布者」。
- 手机端验证使用 390×844 移动视口 + 无头浏览器，**未在真实手机硬件上复测**；配对、刷新、停止走的是与真机相同的 HTTP / WS 路径。
- 「Parallel 批量串位」是 OBS 33.0.1 / obs-websocket 5.7.6 的实测结论；本版无论对端版本都保持串行，性能影响仅是本地几次往返。
- Win7 兼容构建（net6.0-windows / obs-websocket 4.x）未在真实 OBS 27 上复测；旧协议路径本版未改动。
